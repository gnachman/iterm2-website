2026-10-05: Keep a symlinked settings.json when writing the
Claude Code hook. Issue 13098 (#775)

Install, Reinstall, and Uninstall of the Claude Code
Integration wrote settings.json with an atomic write to its
unresolved path. An atomic write renames a temporary file
over the path it is given, so when settings.json was a
symlink into a dotfiles repo (GNU Stow, chezmoi), the rename
replaced the link with a regular file. The link's target
kept its old contents, Claude Code read the new copy from
then on, and the copy did not inherit the target's mode: a
0600 file came back as 0644 on macOS 26.7 (the issue reports
0755 on macOS 27), readable by other users, although
settings.json can hold API keys.

Both write sites now go through one helper that resolves
symlinks before the atomic write, so the rename happens next
to the real file.  The link survives, and the real file
keeps its mode. A dangling link resolves to itself, so
writing through one still replaces it, as before.

The new tests strip the hook through an absolute and a
relative (Stow-style) link and check that the link survives
with the same destination, that the target has the change,
and that the target is still 0600.

2026-10-05: Fix a crash from NSFont keys in the Metal font
ID bijection

-[NSFont it_metalFontID] keyed a bijection by NSFont. A font
made by it_fontByAddingToPointSize: (Cmd-+ and Cmd--) is
-isEqual: to the same font made any other way, but hashes
differently, because CTFontCreateCopyWithAttributes with an
explicit matrix adds an identity matrix attribute to its
descriptor that -hash includes and -isEqual: ignores.
Lookups for the zoomed font usually missed, so it was linked
a second time under a duplicate key, and when that insert
grew the dictionary Swift trapped with
KEY_TYPE_OF_DICTIONARY_VIOLATES_HASHABLE_REQUIREMENTS.

The bijection now recognizes objects conforming to
BijectionIdentifiable, which supply their own identity, and
keys by it while still returning the linked objects.
NSFont's identity is its descriptor attributes, minus a
matrix attribute that is the identity transform, so equal
fonts share one ID and fonts that render differently
(feature settings, variations, a real matrix) keep their
own.

Computing that identity is slow, so the ID is now computed
once and carried with the font. PTYFontInfo computes its
font's ID when the font is set, and
iTermAttributedStringBuilder puts it in the attribute
dictionary as iTermMetalFontIDAttribute next to
NSFontAttributeName, so cheap and NSAttributedStrings both
carry it. The GPU renderer reads the stored ID, which also
removes a lookup it used to do for every glyph.  Only
CoreText runs that use a substituted fallback font still
call it_metalFontID, once per run. The bijection lock is now
an os_unfair_lock.

2026-10-05: Fix crash loops in the window state database
from overlapping saves

A synchronous save (applicationWillTerminate) could run
while an async save was still pending. updateSynchronously:
rejected only async saves while updating, so the sync save
built its delta against the same self.record as the pending
save, and both inserted every node new since then. The
resulting duplicate sibling rows persisted in the database.

On every later launch, for arrays of more than 16 elements,
the delta encoder looked up the previous revision through an
index in which the last duplicate won, while the save
enumerator and restoration take the first. The mismatch
either skipped inserting new children, so the next save
threw MissingRowID and hit fatalError, or paired records
with different rowids and failed assert(before.rowid ==
after.rowid).

A sync save now waits for a pending save to finish and
publish its result before building its delta, so saves never
overlap. The index now keeps the first duplicate, which
stops the crash loop for databases that already contain
duplicates.

2026-10-04: Fix a race that could drop a new session's first
tokens

lazy var.  The reader thread appends tokens while the
mutation queue checks and executes them, and Swift lazy

2026-10-04: Recognize cc-status hook commands that use

inspects it, so users write $HOME/.config/iterm2/cc-status
(to share settings.json between Macs) or a wrapper that
exits quietly when cc-status is missing.  The health check

cc-status entry to each event (issue 13099).

does and finds references to cc-status: a word whose last
path component is cc-status, or a bare cc-status in command

code; such words, and bare names missing from PATH, are

the health check all use it.

cc-status command needs it, so they agree on which commands
are broken and the common case launches no shell. Reinstall
keeps a working custom command and only replaces a plain
absolute path or one that cannot run. The health check is
skipped when the prompt is silenced, and the alert no longer
claims Claude Code rewrote the file.

2026-10-03: Send MacVim an escaped file URL and TextMate the
raw path

Commit 07b59768a made Semantic History send every
scheme-based editor the raw path after file://,
percent-encoded once. That is what TextMate wants, but not
MacVim, and the two cannot share a format:

- MacVim (MMAppController parseOpenURL: and
handleGetURLEvent:) decodes
  the url value once and parses the result with
  URLWithString:, so the decoded value must be a well-formed
  file URL with its path escaped.  Its source calls this
  double encoding the canonical form
  (mvim://open?url=file:///foo%2520bar) and names iTerm2 as
  a tool that sometimes sent a single encode. With the raw
  path a literal %41 in a filename was decoded twice, and
  MacVim builds without the compatibility re-encoding also
  broke on space, # and ?.
- TextMate (handleTxMtURL:) decodes once, strips file://,
and uses the
  rest verbatim as the path. An escaped file URL makes it
  look for a file literally named with %20.

So choose the form by editor: MacVim gets
fileURL.absoluteString, TextMate and BBEdit get the raw
path. Both are then percent-encoded once with & = + # and %
escaped, in a single assignment, with or without a line
number. BBEdit is closed source and is reached through
TextMate's scheme, so it keeps TextMate's form; that is
unverified.

The tests now model each editor's decoding and check the
path it would open for a space, &, #, ? and a literal %41.
The five expected-failure tests from the review are replaced
by passing ones.

2026-09-30: Add the BDSM and SCP escape sequences for
controlling right-to-left reordering (issue 13102)

A full-screen app's row is not a paragraph, so running the
bidi algorithm over it scrambles layouts that contain
right-to-left text. BDSM (CSI 8 l and CSI 8 h) lets an app
switch to explicit mode, where the text it writes is drawn
as written, and back to implicit mode. SCP (CSI Ps SP k)
sets the base direction of reordered lines. This follows
WezTerm's shape: terminal-level values recorded per line as
text is written, not the terminal-wg recommendation's
per-paragraph propagation. Explicit right-to-left layout is
not implemented.

- Lines record the SCP direction in their metadata. It is an
optional
  trailing scalar in both the array and TLV encodings, so
  older and newer builds can read each other's data.
- In explicit mode a write clears the line's RTL flag and
per-cell RTL
  status. The flag is sticky across erases and overwrites,
  so otherwise text an app lays out on a line that once held
  right-to-left text would still be reordered.
- Dropping a line's bidi info also resets its per-cell RTL
status.  - DECRQM reports ANSI mode 8, and both values are
saved with terminal state
  and restored by a terminal reset.
- An advanced setting, on by default, turns both escapes
off.  - tests/bidi-escapes has files to cat for manual
testing.

2026-09-26: Fix Session Note API defects

it has text, including one the user hid and one that only
ever lived in the Notes toolbelt, and -didFinishRestoration
restored all of them. Now that hydration happens early
enough for restoration to actually fire, that meant a hidden
note came back floating. The model gains a mirrored
isVisible, which also bumps generation so the change reaches

whenever the generation has not moved. A missing key
restores as visible, since that is how older arrangements

saved record whenever the generation it is handed equals the
record's, and a model built from an arrangement restarted
near zero while the record kept its old count. The encoder
bumped the record ahead on the first save, and once the

replacements. Clearing a note and creating another handed

key session or its mode changes. It would keep editing a

keystroke. Creating the model from the toolbelt's own

replacing; otherwise the empty new model was reloaded
mid-keystroke and the character lost.

Align the two validators. The pre-check in -[iTermAPIHelper
setSessionNote] looks only at explicitly supplied keys while

another. Two API calls in a row left both timers writing the

newer animation, hiding the scroll view on a note that ended

2026-09-25: Let a session status say when it stops being
true

A program that reports its status out of band cannot
announce every way its work can end. Claude Code is the case
in hand: pressing Esc to interrupt a turn runs no hook at
all, so the tab kept reading "working" or "waiting" until
the next turn, sometimes for many minutes.

Let the program say up front what should happen instead. A
status set through OSC 21337 or iterm2.set_status can carry
expires-on=progress-end plus then-* fields, and iTerm2
applies the replacement when the session reports through the
progress protocol (OSC 9;4) that the operation running when
the status was set has ended. Nothing here knows about any
particular program: the progress protocol is one iTerm2
already parses, and any long-running tool can scope a status
to its own work.

The decisions all live in iTermTabStatusController, which
also owns the session's status object so there is no way to
hold one whose governing state lives elsewhere:

  - A new assertion supersedes whatever the last one asked
  for. An
    update carrying only bookkeeping, such as a
    background-task count, is not an assertion and leaves
    the arming alone.
  - Only the program's own OSC 9;4 reports count, never the
  screen's
    progress property, which also changes on reset. Stopped
    and error end an operation; paused and a bare percentage
    do not.
  - An end waits three seconds before acting, because the
  program's own
    status update travels a much slower path (a hook
    process, then it2, then the API: 0.14s warm, 1.66s cold)
    and its word should win.  Publishing a state the program
    never reported is worse than being a few seconds late,
    since anything watching for a transition acts on it.
  - An expiration is held while the program reports
  outstanding
    background work, and released when that count reaches
    zero.

PTYSession keeps one ivar for all of this and forwards to
it.

set_status's argument parsing is now shared between the
status and the replacement it hands off to, since they take
the same fields. Its error reasons reach the user through
the Script Console, so the new ones are localized like the
rest; each names its own argument in a complete sentence
rather than splicing a fragment into a frame.

2026-09-25: Stop offering to reset key reporting when the
shell manages the mode itself. Issue 13032

for anyone whose shell drives the mode: Fish 4.x arms it
while drawing the prompt, and a prompt tool like oh-my-posh

2026-09-25: Use a server this process launched for new
sessions. Issue 12106

macOS attributes TCC permissions, including Local Network
access, to a process's responsible process. iTermServer
inherits that from the iTerm2 that forked it, and every job
under the server inherits it in turn. When iTerm2 restarts
with sessions still running, after an update, a crash, or a
force quit, the surviving servers are adopted by the new
instance but still name the old, dead process, so anything
they launch is denied local network access with No route to
host.

Restored sessions cannot be repaired: responsibility is
fixed at spawn and there is no API to re-point it. New
sessions did not have to inherit the problem, but did,
because connection selection handed them whatever was first
in the registry, which after adoption is an orphan.

iTermForkedServerRegistry records the socket numbers this
process has launched a server on, which is enough to
establish ownership because every socket belongs to a single
suite: both the application support directory and the dotdir
fallback are per-suite, so concurrent instances use separate
socket directories. Every earlier run's servers already
exist when we start, so if one is listening at a number we
attach rather than launch and never record that number; once
we have launched at a number, only this process can put a
server there. That is why the set only grows and needs no
removal.

- findAnyOwnConnectionCreatingIfNeeded replaces the previous
selection,
  which returned whatever was first in the registry.
- tryCreatingConnectionStartingAtNumber skips socket numbers
already
  registered, since connectionForSocketNumber returns the
  existing connection for those, and keeps walking when it
  finds a live server it did not launch. Those skips get
  their own budget rather than consuming the hard-failure
  count.

Also removes the primary-connection cache. It was a
denormalized pointer into the registry that could go stale
while the registry moved on, and now that ownership is a set
lookup there is nothing worth caching.
findExistingPrimaryConnection had no callers.

Sessions restored from before the restart keep the dead
attribution until they are restarted.

When a display is disconnected, which is what a sleeping
laptop looks like to AppKit, macOS relocates its windows
onto whatever display is left and never puts them back. Lock
Location remembers where a window belongs and restores it
when its display returns.

The anchor is a display, that display's size when the lock
was taken, and the window's frame relative to the display's
origin. Windows whose frame the user chose have the whole
frame defended. Maximized, centered, and edge-attached
windows have only their display pinned, because
canonicalizeWindowFrame computes their frame from whatever
screen they are on and would overwrite a remembered
position; moving them to the right display and letting the
canonicalizer reshape them there is what the user wants
anyway.

A lock also has to know when not to learn. The remembered
frame follows legitimate resizes, and a resize cannot be
told from a move by inspecting it: font size changes,
toolbelt toggles, new splits, tmux layouts, and the Python
API all resize windows with no mouse button down and no
live-resize bracket. So the lock goes dormant the instant
the displays change, on the undelayed notification rather
than after updateScreenParamsDelay, and learns nothing from
a frame until the window has verifiably been put back where
it belongs.

Dragging a locked window releases the lock. The menu item
stays selectable whenever a lock is held, including while
the window is full screen and enforcement is dormant, so it
can always be turned off.

Restoring a window to the Space it was on is not possible
with public API, so a returning window lands on whichever
Space its display is showing at the time. The release note
says so.

Manual test plan in tests/location-lock-manual-test-plan.md.
The disconnect and reconnect behavior has not been verified
on hardware.

CGContext shared by the session and afterwards clears only
the glyph's measured bounding rect. That rect came from
CTLineGetImageBounds, which consults the context's
shouldAntialias flag, but drawWithOffset:iteration: sets

always ran with antialiasing on. In a profile with

aliased and measured antialiased. Monaco 12's "~" draws at y
7...9 while the antialiased bounds claim y 2.18...4.37, far
outside the 2px fudge factor, so ink survived the clear and
contaminated the next glyph rasterized into the shared
context.

iTermASCIITexture builds each texture by walking codes
32...126, so "~" (126) is the last glyph drawn and SPACE

copies the whole cell tile, so the leftover tilde became the
space glyph. The plain texture is built first against a
freshly cleared context; the bold, italic and thin-strokes
textures are built lazily later and inherited the residue.
That is why the reported symptom was bold spaces drawing a
tilde, and why it persisted for the rest of the session once
it appeared.

2026-09-18: Let a conductor command join a pipeline that is
already in flight

Conductor.send() only dispatched when the conductor was
idle. If any command was on the wire, a newly enqueued one
sat in the queue until that command's %end came back from
the remote, which is a full network round trip.
amendPipeline existed to top up an in-flight pipeline but
was only ever called from handleCommandEnd and dequeue,
never on enqueue.

That defeated the point of making framerSend pipelinable
(issue 11266): several keystrokes can be outstanding at
once, but a keystroke could only join a pipeline still being
formed, never one already sent, so typing faster than the
round trip made every key after the first wait one out. In a
debug log from issue 13013, against a host with a 147ms
median round trip, 21 of 40 tmux commands waited over 100ms
before they were even written; the median wait was 117ms and
the worst 428ms.

Extend the pipeline on enqueue instead. The two in-flight
states differ only in which context is executing, so the
shared helper takes a closure to record the new pipeline:
willExecutePipeline replaces its contexts, executingPipeline
keeps the command whose begin was already parsed and appends
behind it. The existing size and pipelinability limits are
unchanged.

Making send() live in the in-flight states meant auditing
every place that mutates a pipeline. They share one shape:
read the pipeline, run a handler that can call back into
send(), write the pipeline back. While send() was a no-op in
those states the shape was harmless. Now a re-entrant call
can install state that the write-back overwrites, leaving
commands on the wire that `state` cannot attribute responses
to, so their handlers never fire.

- extendPipeline: taking contexts off the queue runs the
handlers of
  canceled and aborted ones, and those re-enter.
  handleCheckForPython's cancel arm calls execLoginShell(),
  which calls send(); several arms call fail(), which calls
  forceReturnToGroundState(), so the write-back could also
  resurrect a torn-down pipeline. Collect dropped contexts
  and notify after the state is consistent. Reachable before
  this commit through dequeue() -> amendPipeline([]).
- extendPipeline's write loop: state is consistent there, so
a
  re-entrant send() would extend and write immediately,
  interleaving with the loop. Wire order B, D, C against a
  state of A, B, C, D misattributes D's %begin/%end to C.
  Defer mutation across the loop.
- handleCommandEnd: captures the pipeline from the pattern
match and
  writes the remainder back after running the handler.
  Setting state first, as handle(line:) does, would be
  tidier but changes behavior: handleReset throws
  IgnoreCommandError precisely so an unrecognized command
  end leaves state alone. Guard instead.
- handleUnhook: ran abort handlers with the live pipeline
still in
  state and `state = .unhooked` many statements away. Settle
  state and clear the queue first, as
  forceReturnToGroundState does.
- extendPipeline's nil-delegate path: the old branch only
drained the
  queue and forced .ground, which was safe when nothing
  could be in flight. The executing context lives in state,
  so it was dropped without its handler running;
  performFileOperation's continuation is only resumed from
  that handler, so the awaiting task would hang.  Abort what
  is in flight as well.

Only the first is reachable today. The rest need a future
handler that re-enters, or a synchronous path from write()
back into the same conductor, neither of which exists now.
Enforced rather than left to the audit, since nothing else
records the constraint.

2026-09-18: Fix deferred side-effect flushes never being
armed, and stale timers after a session becomes visible

Three related problems in PeriodicScheduler.

markNeedsUpdate(deferred:) had its guard inverted. It
returned the value of scheduledDeferred from before the
defer block set it, so the first deferred request on an idle
scheduler reported that a timer was already armed and armed
none, while every later one armed a redundant timer. A lone
deferred request has no other scheduling opportunity,
because the hot caller (setSideEffectFlag) only reaches this
on a flag's 0 -> 1 transition and the flag is not cleared
until the side effects run. So on a quiet session a redraw
could wait for an unrelated caller to flush it, which may
never come. Issue 10206.

Rebuild that path on the deadline-and-generation bookkeeping
already used for the throttling reset: at most one deferred
flush is armed, a request no sooner than the armed one
coalesces into it, and a sooner one supersedes it.
Coalescing matters because the side-effect flags hit this on
every linefeed.

Changing period does not disturb timers already armed at the
old one, so a session that became visible could wait out
whatever remained of a background-sized window before its
first paint. Add expedite(within:), which shortens both
armed timers without itself requesting an update, and call
it on the transition to foreground. It deliberately does not
set _needsUpdate: forcing a flush on every tab switch would
cost a sync with nothing waiting. Both timers need it and
they are independent, since a deferred flush can be the only
thing scheduled on an otherwise quiescent session.

Finally, guard period with the mutex. The mutation queue
writes it when a session becomes visible or hidden while any
queue may be reading it, and the deferred path now derives
its deadline from it, so the read and the arm have to happen
under one lock.

2026-09-18: Expedite SSH conductor side effects so they
escape background batching

A session whose view is not in a window batches its side
effects at 1s instead of 1/30s. A tmux gateway never has a
window, so when tmux runs over an SSH profile the conductor
-- which is a strictly serial request/response channel --
advanced at exactly one command per second.

The load-bearing side effect is "end ssh command". It calls
Conductor.handleCommandEnd, which is the only thing that
returns the conductor to ground and dequeues the next
command, and it is a paused side effect, so it also holds
the gateway's token executor stopped until it runs.
Keystrokes are framerSend commands on that queue, and the
echo arrives as TMUX_LINE tokens that the paused executor
will not run, so a round trip paid the full second in each
direction. Debug logs from issue 13013 show every SSH_END
execution landing in handleCommandEnd 1.000s later, and
keystrokes waiting up to 1.2s in the conductor queue.

Add an urgent side-effect tier that opts out of batching,
and move the conductor delegate methods that need it onto
it. Urgent means the flush happens sooner; side effects stay
in the same FIFO and are not reordered.

The recovery handshake is the same shape and is included.
The framer emits one line per process and per saved key
between begin-recovery and end-recovery, and each arrives as
its own paused side effect, so reconnecting a hidden ssh
session would otherwise cost a second per line with all
token execution stalled throughout.

The tier means "a batching period would stall a protocol or
hold a pause", not "belongs to the conductor". That is
narrow on purpose: urgency is a no-op for a visible session,
and because every tier shares one FIFO that is drained
whole, an urgent flush carries everything queued ahead of
it, so a non-urgent side effect is delayed only when it is
the tail with no urgent sibling behind it. So "handle side
channel" and "read raw ssh" stay non-urgent: the former's
command output is always followed by an "end ssh command",
and the latter only feeds a coprocess and gates nothing.

PeriodicScheduler needs to honor an urgent request when a
long reset is already armed, which in the steady state is
almost always. It now tracks the armed reset's deadline and
generation so an urgent request can supersede it, rather
than arming a second reset and allowing two flushes in one
period.

Background batching is otherwise unchanged: visibility still
governs it and still governs token-execution yielding.

units, so the low surrogate was left out of the index set
and the character after it was skipped entirely.

+[NSURL(iTerm) URLWithUserSuppliedStringImpl:] slices the
string by those indices to build its placeholder map, so a
split pair produced a substring holding a lone surrogate.
When that substring came back in a query item,
-stringByAddingPercentEncodingWithAllowedCharacters:
returned nil, because UTF-8 cannot represent a lone
surrogate, and the nil reached
-replaceOccurrencesOfString:withString:options:range:, which
raises. That runs on the mutation queue while executing the
link token, so a URL like https://example.com/search?q=
aborted the app. Session restoration replayed the same link
and crashed again, so the affected tabs could not be
restored.

The index set now takes the whole matched range, which also
stops the following character from being dropped from the
URL. The query loop treats a nil encoding as a failure to
parse the URL rather than passing it along, so no future
ill-formed input can abort the mutation queue.

Fixes issue 13063.

2026-09-17: Honor $CLAUDE_CONFIG_DIR when installing the
Claude Code hook

Claude Code resolves its own settings.json from
$CLAUDE_CONFIG_DIR, defaulting to ~/.claude. That is the
supported way to keep separate accounts (personal vs. work)
on one machine, and we were ignoring it: every read and
write was hardcoded to ~/.claude, so for those users we
installed a hook Claude Code never reads.

The variable lives in the user's interactive rc files, so
reading it means spawning their shell with -i. That is far
too slow for the read paths (menu validation, the
launch-time cache reconciliation, the health monitor), so
resolve it exactly once, at install time, and persist the
answer in NoSyncClaudeCodeConfigDirPath. Everything else
reads that key synchronously. It stays nil until a first
install has run, in which case we assume the default,
matching Claude Code's own behavior and where a from-scratch
install would go.

The onboarding panel starts the resolution as soon as it
opens, so the answer is usually in hand by the time the user
reaches Install. If they get there first, the button bar
shows a spinner and a Cancel button until it lands. A failed
lookup offers a retry rather than guessing a location:
installing into the wrong directory and then recording it as
ground truth is worse than asking again.

Hook installation moves off the main thread. It was already
doing file I/O that can block on a network-mounted home, and
it now has an async step in front of it.

Reinstalling into a different directory strips our hook from
the previous one, so it stops firing from a file no read
path will look at again. That happens only after the new
settings.json is safely written, so a failed write cannot
leave the user with the hook removed from the old location
and not installed in the new one.

User-visible strings that named ~/.claude now interpolate
the real path, with translations updated for all six
locales.

Adds offline tests for the two pure helpers this introduces:
the /usr/bin/env parser and the hook-stripping routine.

2026-09-17: Add interactive mode to shell-script execution
in pidinfo

runShellScript: gains an `interactive` flag. When YES the
shell runs with -i, so the user's interactive rc files
(.zshrc/.bashrc/config.fish) are sourced and the captured
environment matches what a real terminal would have. Callers
that only need the exported environment (PATH,
SSH_AUTH_SOCK) keep passing NO, since sourcing a heavy rc
costs seconds.

Sourcing rc files means the shell's own stdout is no longer
trustworthy: greetings, oh-my-zsh nags, MOTD echoes and the
like write there freely and would corrupt the result. So the
command's stdout is now redirected to a private FIFO inside
a 0700 mkdtemp directory, and the shell's real stdout is
drained and discarded. That makes the captured output exact
on every shell, interactive or not. It also imposes a
precondition, noted in the protocol header: the script must
be a single command, because the appended `> fifo` redirect
would otherwise bind only to the last command of a compound
script.

Completion is now detected from the shell process exiting
rather than from its pipes reaching EOF. Interactive rc
files routinely background a long-lived daemon (ssh-agent,
gpg-agent, powerline-daemon) that inherits the shell's
stdout and keeps the pipe open indefinitely, so EOF may
never arrive.

Other robustness work needed to make -i safe:

- A 15s wall-clock deadline (SIGTERM, then SIGKILL after a
1s grace),
  under the 20s watchdog on the entry point, since a bad rc
  can hang forever. Previously nothing bounded the loop.
- Negative status values distinguish "could not run" (-1
output cap,
  -2 everything else) from a real run's exit status, so
  callers can tell a wedge from a clean run that produced
  nothing.
- The drain helper is bounded in both the capture and
discard cases. The
  old version only bounded the capture case and would spin
  forever discarding output from a producer that keeps the
  fd readable.
- An fd that hits EOF or a hard read error is dropped from
the select
  set instead of being re-polled forever.
- stdin is /dev/null rather than an unclosed pipe, so an
interactive
  shell cannot block trying to read input.

On the app side, runCommandInUserShell: gains an interactive
variant and an XPC error handler, so a caller waiting on the
completion cannot hang forever if the service crashes or is
invalidated mid-call.

2026-09-17: Fix crash saving a debug log containing an
unpaired surrogate

Stopping debug logging threw NSInvalidArgumentException from
-[__NSPlaceholderArray initWithObjects:count:] with a nil
object at index 1, which is the body chunk in
FlushDebugLog's @[ headerData, bodyData, footerData ].

The body came back nil because UTF-8 cannot represent a lone
surrogate, and -dataUsingEncoding: returns nil for a string
containing one even with allowLossyConversion:YES. The lossy
flag substitutes characters the target encoding lacks; UTF-8
lacks none, so it never engages and malformed UTF-16 is
reported as invalid input instead. A single bad character
anywhere in the capture took the whole encode down. Terminal
contents, pasteboard text, and strings built from a
half-delivered UTF-8 sequence all carry lone surrogates, so
debug logs pick them up readily.

DebugLogDataFromString() now encodes, and on failure repairs
unpaired surrogates to U+FFFD and retries. It never returns
nil, since both callers hand the result to something that
raises on nil, so a failure writes a marker rather than
losing the capture. LogForNextCrash had the same latent bug:
-writeData: raises on nil and that path logs arbitrary text.

2026-09-15: Fix crash from autoreleased array of stack
blocks in tab context menu

-[PseudoTerminal tabView:menuForTabViewItem:] built its menu
by collecting the section-builder blocks into an @[] array
and iterating it. This file is manual retain/release, and
those blocks capture locals (self, tabViewItem, rootMenu),
so they are stack blocks. An @[] literal retains its
elements but does not Block_copy them, so the autoreleased
array held raw pointers to stack blocks that die when the
method returns. The array outlives the frame (it drains with
the top-level autorelease pool, after the menu has been
used), and when -[__NSArrayI dealloc] then sends -release to
each element it touches reclaimed stack memory and crashes
with a bad access in objc_release.

-release on a stack block is normally a no-op, so this only
crashed once the stack region had been overwritten before
the pool drained, which is why work-heavy actions like Close
Tabs Below or Add Tab to Group triggered it while lighter
ones did not.

Call the builders directly in order instead of gathering
them into an array, so they run while their frame is still
live and nothing keeps a dangling reference past the return.

2026-09-14: Use synchronous=NORMAL for restorable-state
SQLite

In WAL mode this syncs at checkpoints instead of on every
commit, eliminating a per-commit fsync stall on the graph-db
thread and cutting sustained disk I/O from restorable-state
saves. The only cost is a small durability window: commits
since the last checkpoint can be lost on power loss or
kernel panic (never on an app crash, and the database cannot
be corrupted). Restorable state is best-effort and re-saved
constantly, so being set back to the previous save on a hard
poweroff is acceptable, and avoiding the write pressure
helps keep the process from being jetsammed on macOS
versions that enforce a disk-write rate limit.

synchronous is a per-connection pragma that resets to FULL
on each open (unlike journal_mode, which persists in the db
header), so it is set in createTables: which runs on every
open.

2026-09-12: Coalesce cursor-position and other DSR report
syncs

Issue 13035 reported that CSI 6 n cursor-position queries
were paced one main-thread pause+sync per query, the same as
OSC 4 color queries before they were coalesced. A program
that pipelines a batch of them (the reporter's benchmark,
and notcurses-style capability detection) waited seconds
instead of milliseconds.

Device status reports read either constants or
mutation-thread-owned state that is always current at
token-execution time (CSI 6 n reads the grid cursor), never
the main-thread config snapshot. So they meet the same
criterion OSC 4 does and can share a single sync across a
run.

terminalShouldSendCoalescibleReport: and route the
device-status-report path through it. A run of DSR queries
now pays one pause+sync instead of one per query; any state
side effect in between disarms the skip-sync flag and forces
a re-sync, and the allowNextReport one-shot still delivers
every report on re-execution so nothing livelocks.
Non-coalescible reports (device attributes, cell size) are
unchanged.  Only affects non-tmux sessions: DSR passes
tmuxAllowed=NO, so tmux clients still suppress it.

Extends ReportSyncCoalescingTests: a 200-query
cursor-position burst coalesces to one sync, a cursor query
after a color burst shares that sync, and a genuinely
non-coalescible report (secondary DA) after a burst still
takes its own sync.

2026-09-12: Coalesce OSC 4 color-query report syncs. Issue
13013

mutation and main threads. Terminal multiplexers like tmux

snapshot.

2026-09-09: Sample key reporting flags at FTCS D, not after
the next prompt

Fish 4.x and other shells that use the kitty keyboard
protocol disable it before running a command and re-enable
it when they draw the next prompt. The "key reporting mode
may have been left in an unusual setting" offer compared the
flags at command start against a live read of the flags at
command exit. That live read happened in a deferred
main-thread side effect, which could run after the next
prompt had already turned the protocol back on, so a
well-behaved shell looked like an app that left key
reporting stuck on. Whether it misfired depended on whether
the re-enable was processed in the same token batch as FTCS
D, a race.

Snapshot the key reporting flags on the mutation thread when
the FTCS C and FTCS D tokens are processed and thread those
values through to the heuristic instead of reading the live
value later. At FTCS D the snapshot is 0 for a shell like
Fish (it re-enables only afterward, for the next prompt), so
the offer is suppressed; an app that genuinely crashed with
key reporting on still reads non-zero at FTCS D and still
triggers the offer.

Issue 13015.

2026-09-08: Harden complex-char expansion and add a CoW
mutation check

Two changes aimed at the search-thread crash in
ScreenCharArrayToString (a byte-write fault on the
com.iterm2.search queue during global search):

1. ComplexCharRegistry.expand(string:to:) clamped its
   output to kMaxParts. Every ExpandScreenChar caller sizes
   its destination for at most kMaxParts unichars per cell
   (some pass a fixed kMaxParts stack buffer;
   ScreenCharArrayToString allocates lineLength *
   kMaxParts), but expand did getCharacters with no cap, so
   a stored complex-char string longer than kMaxParts would
   write past the destination. Now it clamps, trimming a
   trailing high surrogate so it never emits half a
   surrogate pair.

2. LineBlock now asserts the copy-on-write invariant
   ("when owner is nonnil or clients is not empty, a copy
   must be made before mutation") on every write to a
   block's shared character buffer or cumulative line
   lengths. This traps a writer that mutates a buffer still
   shared with a reader (e.g. a background search snapshot)
   instead of letting it corrupt the reader later. Compiled
   in only for BETA (debug/beta/nightly) builds, so stable
   releases pay no per-mutation cost: the check becomes an
   empty static function the optimizer eliminates at every
   call site.

Adds a test proving the check does not trip on the correct
copy-then-mutate path.

2026-09-06: Fix Companion reconnect wedge: honor task
cancellation in RelayTransport.receive()

When the phone reconnects and the relay socket is healthy
(keepalive pings succeed) but the mac's bridge has died and
re-parked, the Noise handshake reply never arrives. AppModel
wraps the reconnect handshake in
withTimeout(reconnectHandshakeTimeout), whose timeout leg
cancels the task running NoiseHandshake.perform ->
transport.receive(). Because withTimeout is a task group, it
cannot return until that body task finishes, so the timeout
can only surface if receive() observes cancellation.

Previously it did not: receive() parked on a bare
continuation whose only wakeups were an explicit close() or
a keepalive death. With the ping healthy and the task merely
cancelled, nothing unblocked it, so the handshake and the
whole reconnect loop hung until the user force-quit ("paired
but never reconnects").

Wrap the read-vs-close race in withTaskCancellationHandler
whose onCancel routes into the same cancelAndSignalClosed()
path that close() and keepalive death use: the close arm of

2026-09-02: Add an HDR cursor to the legacy and Metal
renderers

Add a per-profile, per-appearance "HDR cursor" setting
(KEY_HDR_CURSOR, Profiles > Colors) that draws the cursor at
bright HDR white on an EDR-capable display. It is a hint: it
only takes effect when the display has real headroom and the
cursor sits on a dark background; otherwise the normal
cursor draws and cursor boost / smart cursor color still
apply.  This replaces the old experimental "HDR cursor"
advanced setting.

Both renderers agree on appearance: - Shared enablement
predicate and a shared box-frame-only rule so the
  legacy (drawRect:) and Metal paths cannot drift.
- The cursor glyph is drawn bold at the source so
decomposed, regular,
  and ASCII glyphs all get the same treatment regardless of
  RTL or ligatures.
- A shared maximum brightness so toggling the GPU renderer
does not
  change the cursor's peak.
- Smart cursor color is suppressed and the block/glyph AA
are forced
  white where the block is actually filled (not for an
  unfocused hollow box).

EDR engagement is held by a small invisible per-session
keep-alive layer (iTermHDREngager) so that toggling the GPU
renderer or tearing down the Metal view cannot latch the
window out of extended range. It engages only while the HDR
cursor is enabled and the display has headroom, presents a
few frames before latching, retries slowly rather than
giving up, tracks live display changes (screen move, preset
switch, occlusion), and disengages by clearing the flag and
presenting rather than removing the layer.

The Metal framebuffer, pipeline states, and intermediate
textures use fp16 per session when the HDR cursor is
enabled, via a single shared pixel-format helper, and every
margin sub-renderer adopts it so no pipeline is built
against a mismatched target. Flipping the setting live
rebuilds the metal stack. Debug frame capture handles the
fp16 layout.

The Profiles > Colors checkbox still needs to be added to
PreferencePanel.xib and its _hdrCursor outlet connected;
until then the setting is controlled via the profile key.

2026-09-02: Add on-device AI-generated tab titles

Name a tab after the work visible in its session, generated
on-device by Apple Intelligence and published as the
session's "aiTitle" variable. Off by default; enable the
"Name tabs after the work on screen, using on-device AI"
advanced setting, then add the "AI-generated name" title
component to a profile (or interpolate \(session.aiTitle) in
a custom title format). Screen contents never leave the
machine and no API key is used; when the on-device model is
unavailable no title is produced and the session keeps its
name.

The generator is driven from the display-update cadence and
coalesces by rejection: a session with a generation in
flight, or whose screen has not meaningfully changed, is
dropped rather than queued. Change detection uses the
content digest for shells, a background-color histogram for
full-screen apps, and the program's OSC 1/2 title plus
alternate-screen transitions. An idle-progress watchdog
times out only on a lack of forward progress, so a
slow-but-progressing generation is not killed, and a
monotonic epoch scheme keeps a stale generation from
applying its title to a terminated-and-revived session.
Model replies are sanitized before they reach the tab (quote
unwrap, whitespace and control/bidi stripping, length cap).
An opt-in local corpus (off by default) captures inputs for
offline prompt grading.

redundant slashes and handle a root home so an abbreviated
path never contains "//".

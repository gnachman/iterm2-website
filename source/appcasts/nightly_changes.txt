2026-08-26: Fix smooth-blink cursor fading through light
gray in the Metal renderer

The block, underline, and bar cursor renderers used the
default straight-alpha blend, whose alpha channel is
(srcAlpha=SourceAlpha, dstAlpha=OneMinusSourceAlpha).
Filling the cursor cell at a partial fadeAlpha during a
smooth blink dropped the render target's alpha to 1 - fade +
fade^2 (minimum 0.75 at fade=0.5). That partial hole let the
backing show through mid-fade, so a fading black box
appeared to pass through light gray in light mode rather
than fading straight to the background color. The legacy
renderer, which fades the whole cursor as one group, did not
have this problem.

Switch these three solid-fill cursor renderers to
compositeSourceOver (the shadow cursors already used it). It
keeps the alpha at max(src, dst) = 1 while producing the
identical RGB result, because applyFadeAlpha premultiplies
the color for that blend mode, so the fill stays opaque
throughout the fade. The change is a no-op for an opaque
window with a full-opacity cursor.

2026-08-25: Keep a subparameter whose parameter was stored
(#724)

Follow-up to #722 and fd151a4. The overflow flag was set
from the parameter count at the semicolon, but a semicolon
does not always open a parameter: a parameter substring that
starts with a colon takes no slot of its own, and its
subparameters belong to the parameter before it. So after a
full list, CSI 1;...;16;:5 m discarded a subparameter that
belonged to the 16th parameter, which had been stored
perfectly well.

Track whether the most recently opened parameter was stored
instead of whether the list is full. Subparameters are kept
exactly when the parameter they belong to was stored, which
is the rule the two earlier patches were each approximating:

  ;;:5   after 15 parameters  the blank 16th is stored, so
  keep ;:5    after 16 parameters  belongs to the stored
  16th, so keep ;17:5  after 16 parameters  the 17th was
  discarded, so discard ;17;:5 after 16 parameters  belongs
  to the discarded 17th, so discard

I checked this against a model of the documented behavior
written separately from the parser, over 512 generated
parameter lists around the limit: master disagrees with it
on 18, this agrees on 0. The only inputs whose parse changes
are the 18 in that family.

2026-08-20: Bound token-execution memory with a per-token
autoreleasepool

Executing a token can create many autoreleased temporaries.
OSC 133 handling, for example, looks up marks
(lastRemoteHost, lastPromptMark, lastCommandMark) by walking
the interval tree with reverseLimitEnumerator, which
allocates an NSMutableArray per step. execute() drains a
whole batch of queued token arrays in a single GCD block, so
under a firehose (a TUI that clears and repaints every
frame) one call processes tens of thousands of tokens before
its autorelease pool is drained. Those temporaries pile up
into multiple GB of live NSMutableArray and CFString.

Scope an autoreleasepool to each token so the temporaries
drain immediately instead of accumulating across the batch.

Verified on a release-style build driving a full-screen
repaint stream: the process grew to 7.2 GB in about 80
seconds without this change and stayed flat near 400 MB with
it, under the same workload.

Fixes the runaway memory growth in issue 12992.

2026-08-18: Fix blob-replay truncation live test's token
budget

The test lowered AITokenLimit to 8000 to force truncation,
but a terminal-linked chat registers ~25 tool schemas
costing ~5,500 tokens, which maxTokens subtracts from the
budget alongside the conversation.  The system prompt plus
one padded round then pushed even turn 1 over 8000, so every
turn was rejected pre-send with requestTooLarge and no blob
was ever stored (blobCount 0 != 6).

Raise AITokenLimit to 16000 so the tool-schema floor plus a
round fits, and raise AIResponseTokenLimit to 7000 so it
clears that floor too: truncate() budgets maxTotalTokens -
maxResponseTokens and counts only the conversation, not the
tool schemas, so unless maxResponseTokens exceeds the tool
floor the request is rejected before truncation can
activate. With both raised, turn 1 fits, later rounds cross
the truncate threshold, and the oldest round's blob is
dropped from the final request as the test asserts.

2026-08-18: Fix AI chat request bugs on the Responses API
and harden tests

Three related defects surfaced from real OpenAI chat
sessions:

1. Tool schema strict-mode: scroll_wheel and both
register_watch
   variants listed a property in `properties` but not in
   `required`, which OpenAI's strict function schemas reject
   with HTTP 400. The reflection generator (JSONSchema.for:)
   had the same latent flaw for optional fields. Optionals
   are now expressed as nullable-and-required by
   construction on both the hand-authored and generated
   paths.

2. Response parsing crash:
UnkeyedDecodingContainer.decode([Any]) had no
   branch for JSON null, so a null inside an array never
   advanced the container and recursed until the stack
   overflowed. Now consumes null, descends nested arrays via
   nestedUnkeyedContainer, and throws on an unrecognized
   element instead of spinning.

orchestration
   <workgroups> snapshot, the terminal/screen block) was
   folded into the message list as a trailing user message,
   then the Responses builder's previousResponseID suffix(1)
   truncation kept that context and dropped the user's
   actual newest message. Every turn after the first reached
   the model as bare context and it replied as if nothing
   was asked. The volatile context is now passed separately
   and appended after truncation.

serialized wire

2026-08-17: Recognize localhost by any of the machine's

* Fix off-by-one that dropped the 16th SGR trigger parameter

iTermParserAddCSIParameter refused to store a value once

argument

requested parameter: i started at 0, the loop returned on
the first match because i == 0, and the i-- afterwards was
unreachable. It has no callers today, so nothing is broken

subparameter_index other than 0.

When a CSI sequence has more parameters than CSIParam can

had been dropped. iTermParserAddCSIParameter now reports
whether it stored the value.

2026-08-05: Restore sessions whose working directory is gone
(issue 12955)

When a session's saved working directory no longer exists
(for example, it was on an external or network drive that is
not mounted at launch), restoring it could fail to relaunch
the shell and silently close the tab.

Two things went wrong. On the posix_spawn launch path (used
when "Disclaim ownership of children" is enabled), the

the entire spawn. The shell never execs, the session gets an

starting, the tab is closed. This differs from the fork+exec
path, whose chdir() failure is silently ignored so the shell
still launches in a fallback directory.

working directory

  starts, the session shows a banner explaining that it

  ssh (remote paths) and for attach (no shell launch).
- iTermSpawnInitializeActions only adds the chdir file
action when the
  directory exists, so a missing directory can no longer
  abort the spawn.  This makes the posix_spawn path
  best-effort like the fork path and is defense in depth
  against the same directory vanishing after the check.

2026-08-03: Swap the rebuilt uv venv into place atomically

The transactional re-provision built the new .venv aside and
swapped it in with FileManager.replaceItemAt, which is a
multi-step move/backup/move dance with brief windows where
.venv is partial or absent. A concurrent reader (the
Dependency Editor runs `uv pip show` against .venv to
display installed versions) could catch one of those windows
and fail to open a dist-info file (observed as "Invalid
argument (os error 22)" on direct_url.json), surfacing a
spurious [Error] even though the rebuild succeeded.

Swap the freshly built venv with the old one using
renamex_np(RENAME_SWAP), a single atomic syscall that
exchanges the two directory inodes with no intermediate

2026-08-03: Make uv full-environment provisioning
transactional

Changing a uv script's Python version re-provisions its
.venv. The previous code removed the existing .venv before
rebuilding, so if the rebuild's pip install failed (e.g.
downgrading to a Python minor where a pinned dependency such

an empty, broken venv and its working environment was gone.

dependency.

existing .venv is untouched. The venv is created
--relocatable, so the rename keeps its shebangs valid. Fresh
containers (create/import/migrate) have no existing .venv,
so the swap is just a rename.

2026-08-02: Linkify long URLs past the -click capture window
(#706)

When -clicking a plain URL, iTermURLActionFactory only sees
a bounded window of text around the click
(maxSemanticHistoryPrefixOrSuffix, 2000 chars each side,
further clamped to 10 lines). A very long URL (e.g.  7-8k

the URL-legal run reached the edge of the captured suffix

characters and their grid coords are appended to the located
suffix, so the existing punctuation trimming, validation,
and coord mapping all operate on the widened window
unchanged, including the underline drawn on hover.

Add -[iTermTextExtractor
locatedStringByWalkingForwardFrom:characterSet: maxChars:]
and unit tests in ExtendURLSearchResultsTests.

2026-08-02: Keep edge-aligned window width when adding a tab
(issue 12917)

2026-08-02: Fix typo in daemons.rst (#707) 2026-08-02:
Render sixels with a doubled-up ST terminator (issue 12259)

Some tools emit a sixel whose String Terminator is ESC ESC \
instead of the well-formed ESC \. The sixel hook treated the
second ESC as a broken sequence, discarded the entire
accumulated image (VT100_NOTSUPPORT), and left the trailing
backslash to print as a stray glyph.

real hardware and xterm behave (sixels draw incrementally,

nothing rather than
  stamping a broken-image glyph and paying a synchronous

  contains ESC P ... q).

clobbering savedData that a DCS hook already assembled,

2026-08-02: Tmux: correct pane geometry for
pane-border-status (issue 12925)

In tmux control mode the layout string tmux sends the client
reports the full window height for every pane, ignoring the
row tmux reserves for pane-border-status. iTerm2 sizes its
sessions from that layout, so with pane-border-status
top/bottom the session ended up one row taller than the real
pane grid the shell was given: the bottom line went unused
and the cursor landed a row high after reattaching.

Correct the geometry, verified against tmux 3.7b for single,
side-by-side, stacked, three-stacked, L-shaped, and 2x2
layouts:
  top    - a leaf at yoff 0 gives up its first row (yoff +=
  1, height -= 1) bottom - a leaf whose bottom edge is the
  window bottom gives up its last row

Inbound: - TmuxController caches each window's
pane-border-status, learned from a
  new #{pane-border-status} field in the detailed and
  runtime list-windows formats (tmux >= 2.3).
- TmuxWindowOpener parses every layout through
parsedAdjustedLayoutFromString:,
  which applies TmuxLayoutParser
  -parseTree:adjustedForPaneBorderStatus:.
- The zoom/maximize path builds a single-leaf tree from the
uncorrected
  root height, so it applies the same correction there too.

Outbound (keeps the size we report to tmux one row taller so
tmux has room for the border row it carves out, instead of
us shrinking to match the reduced pane and spiraling the
window down a row at a time): - iTermTmuxLayoutBuilder grows
the leaves on the affected window edge,
  which nets exactly one extra row for the window
  (side-by-side panes combine with MAX, stacked with SUM),
  matching tmux's own accounting.
- PTYTab -tmuxSize adds the row back for the refresh-client
-C path.

tmux sends no notification when pane-border-status is
toggled mid-session, so a runtime change is not reflected
until the next relist; the common case of setting it in
.tmux.conf before attaching is handled. The
non-variable-window MIN client size across windows with a
per-window option remains approximate; both limitations are
noted in code.

Adds parser and builder unit tests, including
outbound/inbound round-trip symmetry.

2026-08-01: Report Caps Lock with its Kitty keycode instead
of "A". Issue 12922

Toggling Caps Lock under the Kitty keyboard protocol with
"report all keys as escape codes" enabled sent \e[65u
(codepoint 65 = "A") instead of the Caps Lock functional key
code 57358.

unicodeKeyCode from a switch that listed the
shift/control/option/command keys but omitted kVK_CapsLock,

2026-08-01: tmux: stop injecting focus reports into panes
that never enabled mode 1004

iTerm2 queried the server-global focus-events option once at
attach and, if it was on, force-enabled focus reporting on
every tmux pane by seeding terminal.reportFocus = YES. That
injected stray focus-report escape sequences (\e[O / \e[I)
into every pane on each focus change, even panes whose
foreground app never sent \e[?1004h. With cat -v the
sequences appear as visible input; with a shell they pollute
the prompt (and flip bash's vi mode, the symptom in issue
12352).

The seed was both unnecessary and wrong: tmux forwards the
app's DECSET 1004 in %output, which iTerm2 un-escapes and
feeds to the pane's VT100Terminal, so the per-pane emulator
already tracks focus reporting correctly on its own. Remove
the whole seed chain (the focus-events query and handler,
the _focusEvents ivar, the windowOpener.focusReporting
property, the kLayoutDictFocusReportingKey layout stamping,
and the SESSION_ARRANGEMENT_TMUX_FOCUS_REPORTING arrangement
seed) so tmux panes behave like non-tmux sessions: focus
reporting turns on only when the pane's app requests it.

The one case this cannot reconstruct is an app that enabled
1004h before iTerm2 attached, because tmux exposes no way to
query per-pane focus state; in practice the attach-time
resize causes full-screen apps to re-assert their modes.

Fixes issue 12933.
